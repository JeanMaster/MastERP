# Plan: Restore Client Selection Capability for Cashiers in POS

## Context
A recent security hardening pass introduced role-based access control (RBAC) using `@Roles()` decorators and a `RolesGuard`. As a side effect, Cashier users lost the ability to **search and select existing clients** during sales in the POS, even though they can still **create** new clients.

The user reports:
- Cashiers open the client selector in POS → see nothing (empty list).
- They can still create new clients successfully.
- This worked before the security changes.
- The issue only affects the **selection/listing** flow, not creation.

## Root Cause (Confirmed)
In `apps/backend/src/clients/clients.controller.ts`:

- Class-level guard: `@UseGuards(AuthGuard('jwt'), RolesGuard)`
- `GET /clients` (used by `ClientSelectionModal` via `clientsApi.getAll()`) has:
  ```ts
  @Roles(Role.ADMIN, Role.MANAGER)
  @Get()
  findAll(...)
  ```
- `POST /clients` (create) has **no** `@Roles` decorator → open to any authenticated user.
- `GET /clients/:id` and `PATCH` also have no role restrictions.

The `RolesGuard` (see `apps/backend/src/common/guards/roles.guard.ts`) denies access when required roles do not match `user.role`.

Cashier (`Role.CASHIER`) is a valid role (defined in `roles.decorator.ts`) and is correctly granted access to core sales endpoints in `sales.controller.ts`, but was omitted from the clients listing endpoint during the security pass.

This is a classic case of overly restrictive master-data permissions breaking operational POS workflows.

## Scope of the Problem
- Primary: `ClientsController.findAll()` blocks Cashiers.
- Secondary risk: Similar pattern exists in other controllers (products, suppliers, banks, etc.). Cashiers may hit similar blocks in the future if POS or daily operations rely on those lists.
- The POS client search (`ClientSelectionModal`) and batch sales modal are the main consumers of the blocked endpoint.
- No frontend role gating hides the "Select Customer" button — the failure is purely backend (403 or empty result).

## Goals
1. Restore the ability for Cashiers to search and select clients in the POS without compromising the security intent of the recent changes.
2. Do so with minimal, safe changes and clear rationale.
3. Document any follow-up cleanup needed for consistency.

## Recommended Solution (Preferred)

**Option A – Targeted Allow-List for POS-Operational Read Access (Recommended)**

In `ClientsController`:
- Change the `@Roles` on `findAll()` (and optionally `findOne()`) from:
  ```ts
  @Roles(Role.ADMIN, Role.MANAGER)
  ```
  to:
  ```ts
  @Roles(Role.ADMIN, Role.MANAGER, Role.CASHIER)
  ```

Rationale:
- Cashiers **must** be able to look up and select customers during checkout (core POS function).
- This matches the existing pattern used in `SalesController` (e.g. sale creation endpoints explicitly include CASHIER).
- Creation (`POST`) remains open (or can be left as-is; many shops allow cashiers to quickly register walk-in customers).
- Delete and heavy management actions stay restricted to ADMIN/MANAGER.

This is the smallest, lowest-risk change that directly solves the reported issue.

## Alternative Options (For Discussion)

**Option B – Introduce a dedicated "POS_READ" or "OPERATIONAL" permission**
- More scalable long-term.
- Would require creating a new permission system or expanding the Role enum / adding a permissions array on users.
- Higher effort; overkill for this single symptom unless the team wants to move away from coarse role-based decorators entirely.

**Option C – Keep strict separation and proxy client search through a dedicated POS endpoint**
- Create a new lightweight endpoint (e.g. `GET /pos/clients/search`) that is explicitly allowed for CASHIER.
- Adds indirection and maintenance cost for little gain in this case.

**Recommendation**: Start with **Option A**. It is consistent with how sales operations are already modeled. Revisit Option B only if similar complaints appear for products, suppliers, or other master data that Cashiers legitimately need to browse during daily work.

## Implementation Steps

1. **Update the decorator in ClientsController**
   - File: `apps/backend/src/clients/clients.controller.ts`
   - Add `Role.CASHIER` to the `@Roles()` decorator on `findAll()` (line ~34).
   - (Optional but recommended) Also allow CASHIER on `findOne()` for consistency when a specific client is referenced.

2. **Verify no other client-related blocks for Cashiers**
   - Confirm `create` (POST) behavior is acceptable (currently unrestricted).
   - If policy requires even creation to be controlled, add `@Roles(Role.ADMIN, Role.MANAGER, Role.CASHIER)` explicitly for clarity.

3. **Check for similar issues in other high-traffic master data**
   - Review `ProductsController` (Cashiers need to search products in POS catalog).
   - Review any other endpoints the POS or daily cashier workflow calls that currently exclude CASHIER.
   - Create a small follow-up ticket/list if broader adjustments are needed.

4. **Testing & Verification**
   - As CASHIER user:
     - Open POS → click "Select Customer" → search and select an existing client → should succeed.
     - Create a new client from the same modal → should still work.
   - As ADMIN/MANAGER: no regression on full client management.
   - Run existing client-related tests (`clients.controller.spec.ts`, `clients.service.spec.ts`).
   - Manually test the full checkout flow with a client attached.

5. **Documentation / Comments**
   - Add a brief comment above the `@Roles` line explaining why CASHIER is included (operational POS requirement).
   - Consider adding a note in the security hardening changelog or a "Cashier operational permissions" section.

6. **Deployment**
   - Standard backend deploy.
   - No database migration required (pure authorization change).
   - No frontend changes expected.

| File | Change Type | Notes |
|------|---------------|-------|

## Risks & Mitigations

- **Risk**: Broadening access to client list could be seen as relaxing security.
  - **Mitigation**: Cashiers already handle customer data during sales. Listing is read-only and necessary for the job function. This is narrower than full CRUD.
- **Risk**: Inconsistent role application across master data.
  - **Mitigation**: Document this decision and schedule a quick review pass for products/suppliers if needed.
- **Risk**: Future security audits flag the broad CASHIER access.
  - **Mitigation**: The comment + explicit role list makes the intent auditable.

## Questions for the User (to finalize the plan)

1. Should Cashiers also be able to **update** existing client records from the POS flow (currently `PATCH` has no role restriction), or should that stay ADMIN/MANAGER only?
2. Do you want to keep client **creation** completely open to Cashiers, or should we explicitly add `@Roles(Role.ADMIN, Role.MANAGER, Role.CASHIER)` to the POST for consistency and future policy changes?
3. Are there other master-data lists (products, categories, etc.) that Cashiers are currently blocked from in the POS that we should address in the same change set?
4. Preference on the fix approach: minimal decorator change (Option A) now, or invest in a more granular permission system (Option B) at this time?

## Success Criteria

- A user with role `CASHIER` can:
  - Open the client selector in the POS.
  - Search and see matching clients.
  - Select a client and proceed to checkout.
- No regression for ADMIN/MANAGER client management.
- The change is clearly documented in the controller.
- The fix is minimal and follows the existing pattern used for sales operations.

# Plan Addendum: Toggle to Enable/Disable Barcodes on Price Tickets + Dynamic Density

## Context & Motivation
After implementing Code128 barcodes on price tickets, the user wants to give users (especially those without barcode scanners) the option to **disable barcodes** when generating tickets.

**Benefits when barcodes are disabled:**
- Remove the large vertical blank space reserved for the barcode (~55-90 points).
- Make each individual ticket significantly shorter vertically.
- Increase the number of tickets per A4 page (from current 2×5 = 10 to potentially 2×7 or 2×8).
- Better paper usage and faster printing for users who don't need/scan the codes.

## Current State (After Barcode Implementation)
- `generatePriceTicketsPdf` always generates barcodes (using `bwip-js`) for every SKU.
- Hardcoded layout: `cols = 2`, `rows = 5`.
- Fixed positions reserve space for barcode:
  - Name at `y + 6`
  - Price at `y + 32`
  - Barcode drawn at `y + 55` (height 34)
  - Category near `ticketHeight - 16`
- Barcode pre-generation always happens (async `Promise.all` + cache).

## Goal
Add an optional parameter `includeBarcode: boolean` (default `true` for backward compatibility) that:
1. Skips all barcode generation when `false`.
2. Uses a more compact vertical layout (higher row count).
3. Produces denser, smaller tickets when barcodes are not needed.

## Proposed Behavior

| Setting                  | Rows per page | Approx. tickets/page | Vertical spacing | Barcode drawn? | Pre-generation? |
|--------------------------|---------------|----------------------|------------------|----------------|-----------------|
| `includeBarcode: true`   | 5             | 10                   | Current (with space) | Yes            | Yes             |
| `includeBarcode: false`  | 7 or 8        | 14–16                | Compact          | No             | Skipped         |

## Technical Design

### 1. Backend API Change (catalog.controller.ts)
Extend the request body for `POST /catalog/price-tickets`:

```ts
{
  currencyCode?: string;
  tickets: Array<{ productId: string; quantity: number }>;
  includeBarcode?: boolean;   // NEW - defaults to true
}
```

### 2. Service Change (catalog.service.ts)
Modify `generatePriceTicketsPdf`:

- Accept new optional param: `includeBarcode = true`
- Move barcode pre-generation inside an `if (includeBarcode)` block.
- Make `rows` dynamic:
  ```ts
  const rows = includeBarcode ? 5 : 7;   // or 8 depending on testing
  ```
- In the drawing loop:
  - Only draw barcode if `includeBarcode && t.barcodePng`
  - Adjust Y positions when `!includeBarcode` (e.g. price can sit lower, less padding).
- When `!includeBarcode`, we can also reduce font sizes slightly or tighten margins for even better density.

### 3. Frontend Changes (PriceTicketsPage.tsx + catalogoApi.ts)
- Add a clear toggle (recommended: AntD `Switch` labeled "Incluir códigos de barras").
- Default = `true` (to preserve current behavior for everyone).
- Pass the value in the `generatePriceTickets` call.
- Update the descriptive text (currently says "10 tickets por página").

Suggested UI location:
- Next to the currency selector, or just above the generation buttons.
- Small explanatory text: "Desactiva para imprimir más tickets por hoja (útil si no usas escáner)".

### 4. Performance Consideration
- When `includeBarcode = false`, we completely avoid the `bwipjs.toBuffer` calls → faster generation for large batches.

### 5. Backward Compatibility
- Default must be `true`.
- Existing calls (from any source) continue to behave exactly as today.

## Open Questions for the User (please answer)

1. **Default value**: Should the toggle default to `true` (barcodes on) or `false`? (Current recommendation: `true`).

2. **Density target**:
   - Conservative: 7 rows when barcodes disabled (14 tickets/page).
   - Aggressive: 8 rows (16 tickets/page)?
   - Or make it dynamic based on actual content height?

3. **UI Control**:
   - Preferred component: `Switch`, `Checkbox`, or segmented control ("Con código de barras" / "Sin código de barras")?
   - Should the choice be remembered in localStorage for the user?

4. **Visual feedback**:
   - Update the text below the title to dynamically say "10 tickets por página" or "14 tickets por página" depending on the toggle?

5. **Future extensibility**:
   - Do you foresee wanting more layout presets later (e.g. "Small", "Standard", "Large")?

6. **Other places using price tickets**:
   - Is the generation endpoint used anywhere else besides the PriceTicketsPage (e.g. from mobile app, other modules)? If yes, we must be careful with the default.

## Implementation Steps (High Level)

1. Update backend DTO / controller to accept `includeBarcode`.
2. Refactor `generatePriceTicketsPdf` to accept the flag and compute layout dynamically.
3. Add the UI toggle in `PriceTicketsPage.tsx`.
4. Update `catalogoApi.generatePriceTickets` to forward the flag.
5. Adjust ticket drawing positions and row count based on the flag.
6. Update descriptive texts in the UI.
7. Test both modes thoroughly (especially visual layout and cut lines).
8. Update any related documentation or comments.

## Risks
- Changing row count affects cut-line positioning — must re-verify dashed lines and borders.
- Users who were used to exactly 10 tickets per page may be surprised (hence good default + clear UI text).
- If someone was relying on the exact previous PDF structure for some automation, it would break only when they explicitly turn barcodes off.

## Success Criteria
- User can generate tickets with and without barcodes from the UI.
- With barcodes off → clearly more tickets fit per page (visually verifiable).
- Default behavior (barcodes on) remains 100% unchanged.
- No crashes or layout overflows in either mode.
- Generation is noticeably faster when barcodes are disabled.
