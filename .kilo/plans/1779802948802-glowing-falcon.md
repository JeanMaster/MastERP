# Plan: Restringir Visor de Precios y añadir rol "Vendedor"

Objetivo
- Quitar acceso público (sin login) al Visor de Precios.
- Introducir un nuevo tipo/rol de cuenta "Vendedor".
- Cuando una cuenta con rol Vendedor haga login, redirigirla automáticamente al Visor de Precios.

Contexto y restricciones
- Actualmente el Visor de Precios era accesible sin autenticación; por refuerzo de seguridad se debe eliminar ese acceso.
- No ejecutar cambios ni commits desde este plan (solo instrucciones). El usuario pidió hacer git add y commit antes de comenzar: incluiré la instrucción que debe ejecutarse localmente.

Resumen de tareas (alto nivel)
1. Hacer commit actual (preparación)
2. DB: añadir rol "Vendedor" (prisma/migración o SQL)
3. Backend: soportar rol en DTOs, JWT y guards; proteger rutas del visor y permitir acceso sólo a usuarios autenticados con rol VENDEDOR (o admin si aplica)
4. Frontend: almacenar role en user, redirigir vendedor al visor tras login y proteger ruta del visor (requiere auth)
5. Tests / QA
6. Despliegue y verificación

Detalle técnico y archivos a modificar

1) Commit inicial (obligatorio antes de implementar)
- Ejecutar localmente:
  git add .
  git commit -m "chore: checkpoint antes de implementar restricción Visor de Precios y rol Vendedor"

2) Base de datos (Prisma asumido)
- Modificar `prisma/schema.prisma`:
  - Añadir enum Role { ADMIN USER VENDOR } (nombres en mayúscula o seguir convención actual; propongo `Role { ADMIN USER SELLER }` si el proyecto usa ingles/ES consistente).
  - En el modelo User, añadir campo `role Role @default(USER)`.
- Generar migración:
  - npx prisma migrate dev --name add-user-role
- Notas de datos:
  - Crear al menos una cuenta con role=SELLER (seed o endpoint admin).
  - Si existe una tabla pública de visitantes, migrar/limpiar accesos.

3) Backend (nestjs)
- Archivos/funcionalidades a cambiar:
  - apps/backend/src/users/dto/create-user.dto.ts y update-user.dto.ts: permitir/validar role (solo admin puede asignar).
  - apps/backend/src/users/users.service.ts: persistir nuevo campo role en la creación/actualización.
  - apps/backend/src/auth/auth.service.ts: cuando se firme el JWT, incluir role en el payload (ej. { sub: user.id, username: user.username, role: user.role }).
  - apps/backend/src/auth/jwt.strategy.ts: al validar token, devolver el objeto user con role para que guards y req.user.role estén disponibles.
  - Rutas del Visor de Precios (ej. si hay endpoint público `GET /public/price-viewer`): eliminar/renombrar a `GET /catalog/data` protegido. En este repo hemos visto `apps/backend/src/catalog/catalog.controller.ts` con endpoints `data`, `download` y `price-tickets` — actualmente están protegidos con AuthGuard('jwt') en el controller (línea 17 `@UseGuards(AuthGuard('jwt'))`), así que backend aparentemente ya requiere auth. Revisar si existía algún endpoint público alterno; si existe, eliminarlo.
  - Asegurar `catalog.controller` devuelve 401/403 adecuados si el usuario no está autenticado o no tiene permisos. Decidir política:
    - Opción A (recomendada): permitir que cualquier usuario autenticado pueda ver el catálogo, pero redirigir desde frontend para que sólo los sellers entren directo; o
    - Opción B (más restrictiva): requerir role SELLER (o ADMIN) para acceder a la ruta del visor. Esto depende del negocio. Propuesta: proteger el acceso en frontend (redirigir vendedores al visor), y en backend permitir a usuarios autenticados ver catálogo. Si se quiere bloqueo por rol, añadir guard decorator @Roles('SELLER') con un RolesGuard que verifique req.user.role.

- Validaciones y seguridad
  - Asegurar que solo usuarios con privilegios (ADMIN) puedan asignar role SELLER cuando se creen o actualicen usuarios.
  - Añadir tests unitarios para auth payload y roles si existe test suite.

4) Frontend (React)
- Tipos y API:
  - apps/frontend/src/services/usersApi.ts: extender tipo User para incluir role: 'ADMIN' | 'USER' | 'SELLER'.
  - apps/frontend/src/services/authApi.ts y AuthProvider: asegurar que al hacer login se almacena el user con role en localStorage y en contexto.

- Redirección y protección de rutas:
  - apps/frontend/src/App.tsx: proteger la ruta del Visor de Precios (antes pública). Reemplazar ruta pública por ruta protegida que use el estado de autenticación (useAuth) para redirigir a /login si no está autenticado.
  - apps/frontend/src/features/auth/AuthProvider.tsx: al hacer login, si user.role === 'SELLER' (o 'VENDOR' dependiendo de enum), redirigir a la ruta del visor de precios (ej. '/price-viewer' o donde esté). Implementación: tras login y setUser, ejecutar navigate('/catalog/preview') o la ruta correspondiente.
  - apps/frontend/src/features/auth/LoginPage.tsx: no requiere cambio funcional más allá de conservar role; opcionalmente mostrar mensaje si es vendedor.

- UX responsive / mensajes
  - Para vendedores, la experiencia debe ser directa: login -> visor. Añadir pequeño banner o texto explicando que los vendedores acceden al visor.

5) Endpoints administrativos / creación de vendedores
- Añadir API REST para que un admin cree cuentas con role SELLER (users controller ya existente). Alternativa: usar UI de Users (UsersPage) para seleccionar role al crear usuario.
- Añadir validación en frontend UsersPage / UserFormModal para permitir seleccionar el rol (solo mostrado a administradores en la UI).

6) Tests y QA
- Unit tests:
  - AuthService: JWT payload incluye role.
  - RolesGuard (si se implementa): acceso permitido/denegado según role.
- E2E / integración:
  - Flujo: crear cuenta vendedor -> login -> redirige al visor.
  - Intento de acceso al visor sin auth -> redirigir a login.

7) Migration / despliegue
- Orden recomendado de despliegue:
  1. Hacer commit local de cambios actuales (checkpoint).  (git add . && git commit -m "chore: checkpoint before seller-role implementation")
  2. Implementar cambios backend y tests, ejecutar migración de BD (npx prisma migrate dev --name add-user-role) en entorno de desarrollo.
  3. Desplegar backend (staging), ejecutar migración en staging.
  4. Ajustar/crear accounts seller (seed o admin UI).
  5. Implementar cambios frontend que esperan el nuevo JWT (incluir role). Hacer build y desplegar frontend.
  6. Verificar en staging y luego production.

Caveats y decisiones a confirmar
- ¿El rol se llamará "Vendedor" (ES) o "SELLER"/"VENDOR" (ENG)? Mantener consistencia con el código existente.
- ¿Desean que solo usuarios con role=SELLER puedan ver el visor (backend enforcement), o solo que al loguearse los vendedores sean redirigidos al visor y la ruta quede protegida por auth (cualquier usuario autenticado)? Recomendación: aplicar protección por auth (cualquier usuario autenticado) y opcionalmente RolesGuard si se requiere más restricción.
- ¿Quién puede crear cuentas Vendedor? Proponer: sólo administradores. Necesitamos habilitar UI para asignar roles (UsersPage) y/o endpoint admin-only.
